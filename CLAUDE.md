# Resonate

A vocal pitch + waveform web app served over LAN so it can be used from a phone. Sing into the mic, see the note name, cents-off, volume, and live waveform.

## Deploy (primary workflow)

Push to `main` → `.github/workflows/deploy.yml` publishes `public/` to the `gh-pages` branch → live on GitHub Pages (HTTPS, so the mic works on a phone with no cert hassle). This is the normal iteration loop: make the change, bump the version badge, push to `main`, tell the user when the deploy finishes. The local server below is only for offline testing.

## Pages

- `index.html` + `app.js` — the tuner (hold a note, see note/cents/volume/waveform). Classic script with its own YIN — deliberately untouched by the other pages. Header links to Record and Sing. Start sets `navigator.audioSession.type = "play-and-record"` before `getUserMedia` (**iOS keeps a page's audio-session type for the whole tab**: after Sing set `playback` for the piano, the Tuner's Start used to fail silently — its error was also overwritten by stop()'s "idle"; now shown after stop()), Stop/pagehide set `auto`; an 8 s watchdog re-enables Start if the mic never answers (a late answer still starts unless Start was tapped again — `startGen`). Every page that sets the session (Sing, Record, Voice) sets `auto` and closes its playback context on `pagehide`. tools/tunerfix.cjs. iOS Safari asks for the mic once per page load unless the site is set to Allow (aA → Website Settings → Microphone).
- `record.html` + `record.js` — free singing: live piano roll, transcript of detected notes, playback (voice / notes on piano / both).
- `sing.html` + `sing.js` — karaoke against a MusicXML song: the score sets the clock, you sing along, each note is graded in its own time slot.
- `voice.html` + `voice.js` — **Voice profiles** (linked from the Tuner's profile chip): create/rename/delete named profiles; volume calibration (two guided holds, same measure as the Tuner's gear: quiet = 25th, loud = 90th percentile of dB above −50 over 2 s); **range test**: the piano plays a note, you sing it back and hold it (800 ms within 50¢, up to 6 s; mic ignored while the note plays + 0.35 s). It starts from a steady comfortable note you sing (1.2 s), walks down by whole tones, a miss gets one more try, after two misses the semitone in between is tried, then the same going up (A1–C6 bounds = the YIN range). **iOS plays sound very quietly (earpiece / ducked) while a page has the mic open** (WebKit bugs 196539, 218012, 230902; full volume returns once capture stops and `audioSession.type` is `playback` again — 236219), so the range test captures only while you sing: before each reference note it stops the mic tracks and sets `playback`, plays the note (piano + held tone via `holdPiano`, 1.2 s, level 2.0 ≈ 6 dB above Listen), then reopens the mic (`play-and-record`) into the same analyser. Its two AudioContexts (playback, analysis) are created and resumed in the tap that starts the test so they can run later without a gesture; `pitch.js` `createReader(analyser, sampleRate)` is the shared frame reader. A newer playTarget call (Hear again, next note, Stop) supersedes an in-flight one (`seq` token). voicetest.cjs checks no reference note starts with a live mic track. The Sing page's count-in clicks / melody guide still play with the mic open (same quietness on iPhone; headphones avoid it). Limits = lowest/highest held; comfortable = ~15% of the span inside each limit, adjustable with −/+ steppers (tap a note to hear it); voice-type presets (Bass…Soprano) without testing. `window.resonateDebug()` exposes the test state (tools/voicetest.cjs drives it with an oscillator as a simulated singer).
- `profiles.js` — profile store in `localStorage` (`resonate.profiles` = `{ active, list: [{ id, name, vol: {floor, ceiling}, range: {low, high, comfortLow, comfortHigh, at} }] }`). The first profile inherits the Tuner's old `resonate.volCal`. The Tuner (`app.js`, classic script) reads/writes the active profile's `vol` directly (falls back to `resonate.volCal` while there's no profile) and shows a profile chip.
- `fit.js` — `fitToRange(notes, range)`: fit a melody into a profile's comfortable range (see Sing).
- `tools.html` — Tools menu (debug/experimental): links to tools + a device-capability check. Every page's header links here.
- `pdf-import.html` + `pdf-import.js` — **PDF → Song**: runs Audiveris (Java OMR) in the browser via CheerpJ and saves the MusicXML to My songs (see "In-browser OMR" below).
- `omr/` — the in-browser OMR engine (`omr.js` page side, `omr-worker.js` + `ocr-engine.js` in a Web Worker, `pdfprep.js`, jars, WebAssembly Tesseract, pdf.js). Built from `/omr-build` (not published).
- Shared ES modules used by record + sing:
  - `pitch.js` — `openMic()` (mic with processing off, AnalyserNode, `read()` → `{rms, db, midi}`) and the YIN detector. Same algorithm/settings as `app.js`.
  - `music.js` — note names, `fold` (octave-free semitone difference), `median`, `centsLabel`.
  - `piano.js` — sample piano (`loadPiano`/`playPiano`) and a noise-burst metronome `playClick`.
  - `capture.js` + `recorder-worklet.js` — capture a take's raw audio for playback; `playVoice`.
  - `musicxml.js` — MusicXML parser with timing (`.musicxml`/`.xml`, zipped `.mxl` via a tiny zip reader + `DecompressionStream`; UTF-8 or UTF-16).
  - `library.js` — "My songs": imported scores (raw XML) in IndexedDB, in-memory fallback.
- `songs/` — bundled sample scores (see `songs/README.md` for licensing). Add to `SAMPLES` in `sing.js` and an `<option>` in `sing.html`.
- `piano/` — piano samples (see below).

## Run (local, optional)

```
cd C:\Data\Claude\resonate
npm start
```

Server prints both HTTP (port 3000) and HTTPS (port 3443) URLs for localhost and every detected LAN IPv4. **In practice the port that matters is 3443 (HTTPS)** — that's the one used from a phone, because `getUserMedia` is blocked on insecure origins for any non-localhost host. Port 3000 (HTTP) is only useful for localhost testing. There's no auto-reload; restart the node process to pick up `server.js` changes. Frontend changes (`public/`) just need a browser refresh.

**Which Network URL to give a phone:** the banner lists *every* IPv4, including virtual adapters — Hyper-V's "vEthernet (Default Switch)" (`172.x`) and VirtualBox host-only (`192.168.56.x`). A phone can't reach those. Pick the **Wi-Fi adapter's** IP (the one on the same subnet as the phone).

**Restarting:** `server.js` calls `listen()` with no `error` handler, so if an instance is already running, `npm start` prints the banner and *then* crashes hard with `EADDRINUSE` on 3000. A running instance holds both 3000 and 3443 — so this error also means "it's already up." To restart cleanly, kill the existing `node` process first (`Get-Process node | Stop-Process`).

## Version marker

`index.html` shows a `v<N>` badge in the top-right of the header (`#version`, purple). It exists so you can confirm a frontend change actually reached the phone — bump the number, refresh, check the badge. To bump: edit the `<span id="version">` line in **every** page — `index.html`, `record.html`, `sing.html`, `tools.html`, `pdf-import.html`, `voice.html` (keep them equal). If the badge doesn't change after a refresh, the phone is serving a cached `index.html` — hard-refresh / pull-to-refresh.

## Stack

- Node 21+, ESM, Express 4, `selfsigned` for cert generation
- Vanilla HTML/CSS/JS frontend, no build step, no framework
- Web Audio API (`AnalyserNode`, fftSize 4096) for capture; YIN for pitch detection; Canvas 2D for the waveform

## HTTPS / self-signed cert

Generated on first run to `certs/cert.pem` and `certs/key.pem`. SAN includes `localhost` and every IPv4 present at generation time.

**If the LAN IP changes** (router lease, network switch), the cert won't cover the new IP — delete `certs/` and restart to regenerate.

Browsers warn ("not private") because the cert isn't CA-signed. On iOS Safari: "Show Details" → "visit this website".

## Windows firewall

If the phone can't reach the server, this is the most likely cause. Allow inbound on 3000 and 3443.

## Pitch detection (`public/app.js`)

YIN algorithm (de Cheveigné & Kawahara, 2002). Chosen over FFT peak-picking because YIN avoids the octave errors that vocals trigger. Inner loop is bounded to `tau ∈ [minTau, maxTau]` covering only the vocal range (~50–1100 Hz) — keeps it cheap enough for phones.

`detectPitch` sets `halfN = buf.length - maxTau` so the autocorrelation uses every sample the largest lag will allow, instead of the standard `buf.length / 2`. This is what makes low-pitch detection viable at fftSize 4096; reverting halfN to `buf.length >> 1` halves the cycles available for sub-100 Hz pitches and the dip stops triggering. The threshold for accepting a YIN dip is 0.2 (paper suggests 0.1–0.15; relaxed because low-fundamental vocals often don't dip below 0.15).

Mic constraints disable `echoCancellation`, `noiseSuppression`, and `autoGainControl`. Browser defaults distort pitch and amplitude in ways that break detection and meter scaling.

## Locked-note display logic

The shown note isn't `round(current pitch)` — that flickers when vibrato lands near a semitone boundary and lags badly when the user intentionally jumps to a new note. Instead:

- `lockedNote` is a single integer MIDI we currently display.
- Cents number + needle = long-window median (1.5 s) compared to `lockedNote`.
- Each frame, the **short-window median** (300 ms) is compared to `lockedNote`. If it's >50¢ off, an off-note timer starts and the note dims (`data-onnote="false"`).
- If the short median stays >50¢ off for **250 ms**, we re-lock to `round(short median)` and trim history older than the short window so the long median resnaps.

Net feel: holding a note is rock-stable; intentional jumps cause a brief dim then a clean snap.

## Tunable constants (top of `public/app.js`)

| const | default | effect |
|---|---|---|
| `PITCH_WINDOW_MS` | 1500 | long smoothing — bigger = more stable cents number, slower settle |
| `SWITCH_WINDOW_MS` | 300 | live-pitch window — smaller = more reactive but jitterier |
| `SWITCH_DELAY_MS` | 250 | grace period before snapping to a new note |
| `MIN_RMS` | 0.012 | loudness gate — raise if room noise produces false readings |
| `MIN_CLARITY` | 0.80 | YIN clarity threshold — raise for stricter readings |
| `MIN_FREQ` / `MAX_FREQ` | 50 / 1100 Hz | vocal range bound for YIN; sets `minTau`/`maxTau` |

## Volume meter

Maps RMS → bar width via `(dB + 55) * 2`, clamped 0–100%. Roughly −55 dB empty, 0 dB full. If the bar sits too full or too empty for your mic gain, adjust the `+55` constant in `updateVolumeMeter()`.

## Record page note segmentation (`public/record.js`)

Per frame: YIN pitch (`pitch.js`, same settings as the tuner) → median over `SMOOTH_MS` (100 ms). A note continues while the smoothed pitch stays within 50¢ of the note's median; it splits when the pitch sits >50¢ away for `SPLIT_MS` (80 ms), and ends on an unvoiced gap ≥ `GAP_MS` (70 ms). Notes shorter than `MIN_NOTE_MS` (60 ms) are dropped. Voicing also requires the RMS of the newest `TAIL_SAMPLES` (1024, ~21 ms) to pass `MIN_RMS` — the full 4096-sample window smears short gaps, which otherwise merges repeated same-pitch notes. No beat grid yet; times are seconds.

## Sing mode (karaoke, `sing.js`)

The **score is the clock** (an earlier version aligned sung notes to the score ignoring rhythm — dropped: wrong notes leave nothing reliable to align on).

**Parsing (`musicxml.js`):** picks the part+voice with the most lyric syllables (the melody — e.g. soprano of an SATB hymn). Tracks position across all voices (`backup`/`forward`) so each note gets an `onset` and `dur` in quarter notes; measure starts in `measures` (a short first measure = pickup). Keeps the highest note of chords, skips grace/cue notes, merges ties — and also merges the first note of a new system/page (`<print new-system|new-page>`) into the previous sung note when it has the same pitch, no syllable in any verse and no rest between: a tie split by a line break, which OMR (Audiveris) often loses across pages; rests become gaps (and `restBefore`). Tempo = first `<sound tempo>` or `<metronome>` (default 90 if none), time signature from the first `<time>`. Lyrics per verse; a note with no syllable after a sung one is a melisma continuation (`‿`). **Repeats are followed** (`readStructure` → `performanceOrder` → `unfold`): barlines (repeats with `times`) and directions (segno/coda signs, `<sound>` segno/dalsegno/dacapo/tocoda/coda/fine, words "D.S."/"D.C."/"To Coda"/"Fine") are read from every part, `<ending>` brackets from the top part only (they're drawn above the system; Audiveris reads piano 8va lines as endings on lower staves — Wichita's piano had three); ending numbers "1, 2" / "1.2.3." are lists, "1-3" and Audiveris's "1,,3" (its export of a printed "1.-3.") ranges. A repeat goes back to the last forward repeat (or the start, or just after the previous repeat) and plays `times` times, or one more than its ending's highest number, and — when no D.S./D.C. comes back — at least as many times as its section has verses (max 8); an ending plays on its numbered passes, one past all its numbers that doesn't repeat is the final ending; a 1st ending that stops just before its repeat sign runs to it (Wichita: Audiveris put "1." on m21 only, the repeat is at m22); after a D.S./D.C. repeats aren't retaken, first endings are skipped, To Coda jumps to the Coda, Fine ends; D.S. with no segno found is ignored. Each played measure gets a verse *pass*: the pass of the repeat it's in, 1 for new music after a repeat or a final ending, after a D.S./D.C. one more than the times its target was sung. A note sings verse k if it has it; after the last verse-k word of its measure, the latest verse it has when the following music has no verse k (a refrain printed once under line 1); in the last measure before a repeat sign, the next verse's word (a pickup printed on line 2 in a 1st ending); a measure with no verse k at all sings the latest verse it has. The chosen syllable becomes verse "1" (`score.verses` = ["1"], so the verse menu disappears) and `score.unfolded` = {written, played, passes} — unless the song has stacked verses no pass reaches (a hymn with a repeated refrain): then the written order and the verse menu stay. A note tied across a jump (into a 1st ending, over To Coda) is cut at the jump; a note right after a jump starts a new lyric line only if a rest precedes it (Wichita's "small va-ca-tion" stays on one line). Wichita: "…small va-" → back to the verse for "-cation, but it don't look like rain" (pass 2, refrain words reused) → 2nd ending → Coda (its repeat twice). Killing Me Softly: 69 written → 107 played measures (verse/chorus twice, bridge, chorus repeat); only verse-1 words in the score, so pass 2 repeats them. tools/repeatcases.cjs (20 cases: endings, AABB, intro vamp, no forward sign, D.S./D.C., hymn, refrain pickup, 1st-ending pickup, tie cut), tools/flow.cjs (a song's lyric lines in performance order). Lyric text cleanup: verse numbers stripped, `I 'm` (often with a non-breaking space) → `I'm`. `lyricLines()` splits a verse into display lines at rests and line-ending punctuation. Title falls back to the largest-font `<credit-words>`.

**Session:** one AudioContext for mic + guide so clocks match. Count-in = one bar (+ the missing beats of a pickup bar) of clicks; `songT0` = song time 0 on the audio clock. Guide while singing: **click** (default — a noise burst, so speaker bleed into the mic isn't read as pitch), **melody** (piano; use headphones or the mic grades the piano), **none**. Settings: verse, transpose, tempo (50–125% of the score's), persisted in `localStorage` (`resonate.sing.*`). **Transpose** (−12…+12 semitones, remembered per song in `resonate.sing.keys`; the old global `resonate.sing.transpose` is migrated to the song that was open) works like a notation editor: `transposeKey` (music.js) picks the new key with the fewest accidentals (ties → flats) and the interval's size in letters, and `spellTransposed` moves each note's *written* spelling (the parser keeps `letter`/`alter`) by that interval — C minor +2 = D minor, A♭→B♭, leading-tone B→C♯ (double sharps/flats respelled). Options name the key they land in ("Key Cm", "+2 Dm", "−12 Cm 8vb"; major/minor from `<mode>`, else the final chord's bass (`score.finalBass`, lowest note of the last measure with notes, all parts) or the melody's last note when it's one of the two tonics the signature allows, else the tonic the melody dwells on — Wichita Lineman ends on B♭maj7 and its melody dwells on D, but the melody ends on F: F major; PDF → Song also writes `<mode>` from a Musicnotes file name's "…_F_Major_…"). Chips, the target readout and lyric-less note names use these spellings; the summary shows the transposed range (lowest–highest). Pitch itself (targets, guide, Listen, grading) is just `midi + shift`. **With a voice profile the transpose menu shows what fits** (`fitOptions`, fit.js): every whole-song shift −24…+24 plus, for each key s (−6…+5), its best *split* — one key for the song, whole phrases moved by their own octaves (phrases split at rests and at leaps > an octave — singers handing over without a rest), chosen exactly by DP per key — when the split beats singing that key whole. Groups: **Fits <name> (C3–E4)** (< 2% of the sung beats outside the comfortable range, none beyond the limits), **Close** (< 15% out, < 2% beyond; or "Closest for <name>" when nothing fits), then **Other keys** (−12…+12 whole), and for a song whose best option is a split (a duet on one staff), **Other keys, parts split** (each key's split, e.g. its own key) first. Sorted by cost: beat·semitones outside the comfortable range 1/semitone, beyond the limits +4, within 2 semitones of a comfortable edge 0.25, changing octave between phrases 24, moving at all 0.02 per beat·semitone. Labels name the landing key and mark the song's own key ("−12 A♭ · same key", "−10 B♭", splits as "+17 / −7 Fm · 5% out") so you can choose staying in key over the closest fit. Values: a number (whole-song shift) or `"fit:s"` (key s split, re-solved on load with `fitKey` so it follows the profile); v32's single `"fit"` is converted to the option `fitToRange` picks. Picking an option says under the song bar how it fits ("Down an octave, in A♭ (the song's own key). Fits Dave's comfortable range" / "16% of the singing is outside…"; splits: "the low part (61 phrases) up…, the high part (14 phrases) down… — both in Fm"). Without a profile range the first option is "Fit my range…" (links to the Voice page). Songbird (Hades F1–C3, Eurydice G3–B♭4) for a baritone C3–E4: closest Fm split +17/−7 (5% out); its own key Cm +24/+12/−12 (7% out). Notes get per-note shifts (`shifts`); a take's grades are kept only while `shiftSig` and tempo match.

**Loading songs:** **Open** button (a direct tap → `fileInput.click()`; iOS blocks file pickers opened from a `<select>` change, which is why there's no "Load…" menu item) with **no `accept` filter** — iOS greys out `.musicxml`/`.mxl` since it has no file type for them; files are validated after picking, with specific hints for `.mscz`/`.mid`/`.pdf`/`.sib`. **Link** (prompt; GitHub `blob` URLs → raw, Dropbox → `dl=1`; CORS failures explained). Drag-and-drop on desktop. Imported songs go to **My songs** (`library.js`, IndexedDB, stored as raw XML and re-parsed on load); ✕ removes; **⤓** downloads the current song's stored MusicXML (share sheet on touch devices — Save to Files / send to an app — else a `.musicxml` download), e.g. for the user to send a converted song back for comparison. The old single `resonate.sing.customXml` localStorage song is migrated once.

**Entry bar:** the count-in, clicks, lane and Listen start at the bar containing the first sung note (`entryIdx`/`entryT`), so songs with an instrumental intro (e.g. art songs) don't make you wait through it. `songT0` is offset so song time stays absolute.

**Frame timing:** `frameT = songT − ANALYSIS_LAG − latency`, where `latency = outputLatency (or baseLatency) + INPUT_LATENCY (20 ms)` — the singer follows what they hear late, the mic hears them late, and a pitch frame lags its audio.

**Grading (`grade.js`, v44):** each note's slot may move — its start up to `MAX_SHIFT` (0.24 s) either way in 30 ms steps, chosen for the whole take at once by dynamic programming over the notes (they stay in order, a moved slot keeps ≥ 40% of its length; moving costs `MOVE` 0.15/s, changing the shift between joined notes `DRIFT` 0.1/s, across a rest 0.03/s), cost = note length × share of frames not within 50¢ over the *whole* slot, plus time the note was sung in an adjacent rest (so early entries / held-over ends are found). A rusher's right notes used to land in the neighbouring slot and be marked off: a simulated singer 150 ms early on Amazing Grace scored 62% (9 off, 3 missed) before, 97% after. A note is then judged on its moved slot minus the grace (`min(120 ms, 25%)`): voiced ≥ 35% → median octave-folded deviation ≤25¢ good, ≤50¢ close (ok), else off; else loud-but-unpitched (rms ≥ `MIN_RMS`) + voiced ≥ 50% → **unclear** ("couldn't hear the pitch" — not counted in the %; dotted chip, light blue), else missed. Grades carry `shift` (s, − = early), `from`/`to` (the moved slot). `hit` = share of the slot's frames within 50¢; the take's % (`takeScore`) = duration-weighted mean `hit` over notes not unsung/unclear. Summary adds "· N UNCLEAR" and "· EARLY/LATE ~.15 S" (`timingTendency`: median shift of in-tune notes, shown from 80 ms). During the take a note is graded alone (`gradeLive`, its best shift) once frames pass its end + `MAX_SHIFT`; at the end `gradeTake` regrades all and the pitch line is recoloured against each frame's matched note. Lane: a short line above a bar shows where you sang it when ≥ 80 ms early/late. Frames keep `rms`. Notes after Stop (first half not reached) are *unsung*. Octave sung is reported (8vb/8va). tools/gradecases.mjs (node: in time, early, late, drifting, silent, unclear, wrong, flat, octave, stopped, too early, 450-note speed ~40 ms), tools/gradeearly.cjs (browser, simulated singer with OFFSET and NOISE notes).

**Display:** lane with the "now" line at 30%; score notes as bars with lyrics; your pitch drawn octave-shifted next to the current target (green within 50¢, red outside). Karaoke lyric line above (current syllable yellow, graded syllables coloured). Chips per score note (a held syllable — melisma — shows a short extender line instead of a word, so a long run reads like the score's "line. ____", not a row of ‿) are **piano keys** (`pressKey`/`releaseKey`/`cancelKey`): touch-down (pointerdown) starts the note — the same piano Listen plays, current key — and it sounds until the finger lifts (min 0.25 s; auto-release after 60 s if a release is ever lost); each pointer is its own key (two fingers = two notes). The piano samples die away fast (A4 is ~35 dB down after 1 s, and they end at 3 s), so `holdPiano` (piano.js) adds a steady tone (harmonics ≈ 1/n^1.2 up to 12, boosted up to ×2 below middle C — a phone speaker barely plays below ~200 Hz) fading in under the piano; `release(at, tc)` may be called again with an earlier time. Releases are heard on the window and on the chip itself (WebKit sends a touch's end to its original, possibly replaced, chip). Scrolling the chip list from a chip: on pointercancel the note is cut (τ 10 ms) and the cursor goes back; a touch within 150 ms of a chip-list `scroll` (stopping a fling) is ignored. During Listen/Play only a *click* (a real tap, not a scroll) jumps playback there; ignored while singing; keys still sounding when Listen/Sing start are silenced (`stopKeys` after the session starts too). A click with `detail === 0` (keyboard, assistive tech) plays it for its length in the song. Chip, syllable and lane bar are lit while held and the cursor moves there; the chip list isn't rebuilt, so its scroll stays put. Chips: `touch-action: pan-y pinch-zoom`, no text selection / callout. iOS (and the spec) only allow audio to *start* on a touch's end, so the first tap or key anywhere on the page (`unlockPlay`; not the Sing button or while singing) resumes the play context — without setting the audio session, so other apps' music isn't stopped before a note plays — and loads the piano; if the very first touch is a chip press it may sound only at lift-off (then for its song length), and a press still silent 1.5 s after the lift is dropped, not played late; a note called off before its start time (`release(at ≤ when)`) is silenced outright (cancelling its start events alone left the gains at full volume for an instant); `getPlayCtx` also resumes an `interrupted` context. Test: tools/chipkeys.cjs (CDP touch holds, two fingers, scroll cancel + cursor restore, Listen tap vs scroll, keyboard repeat). **🎤 Pitch** (results row, `monitorOn`/`monitorOff`/`monitorSync`): a live readout of the note you're singing, any time — big note name coloured against the *practice note* (the chip pressed last, `practiceJ`; any octave: green ≤ 25¢, purple ≤ 50¢, red + ↑/↓ otherwise), cents off the nearest note, and on the lane a dashed line at the practice note's row plus your pitch over the last seconds running back from the now line (moved by octaves next to it). Median of the last 0.2 s of YIN frames (`currentYou`). With Pitch on, a take shows the same readout from the take's mic, against the note due at the middle of that window (the target switches when the shown pitch does — comparing with the newest frame's note flashed red at every note change). The readout stays in the layout (invisible) during Listen/Play so the lane doesn't jump; `.results-head` wraps (#you + button on their own line on a narrow phone) and `#chips` shrinks rather than run under the footer. A review keeps the take's pitch line (dimmed under the live trail); a graded note keeps its grade outline instead of the practice highlight. Because iOS plays quietly while the mic is open, the monitor's mic (its own AudioContext, made in the tap) is closed whenever anything plays: a key goes down (the note starts 0.1 s later, so the speaker takes over), Listen/Play/Sing start (`starting` = "play"/"sing" while they set up); turning Pitch on while something sounds puts the session straight back to `playback`; an open interrupted by a key etc. (`m.gen` bumped on every close) is dropped when it settles — even a rejection, since `playback` may have caused it — and retried, never reported — and reopens 300 ms after the last key is let go / the session ends, ignoring the first 150 ms; while a key sounds the readout shows the note to match ("listen…"). Off when the page is hidden. Not remembered (opening the mic on load would prompt). tools/pitchmon.cjs (simulated singer, fake audio session: notes start with no live track, playback session). **Review (v45, `coach.js`):** after a take a bottom sheet opens (also the **Review** button next to Play): the take's %, ▲/▼ vs the previous take of this song (`resonate.sing.history` = { songId: last 10 takes [{ sig (verse|notes|lines), at, pct, lines: [score\|null] }] }), the summary, a one-line tip when the whole take ran ≥ 0.1 s early/late, then **Work on these** (up to 3 weak lines: score < 85% or a missed/unclear/timing reason, ranked with unclear time as half right) with every reason, and **Every line** (first reason). A line > 50% unclear shows "?". Each line: ▶ You / ▶ Melody (/ ▶ Both) plays just that line (`startPlay(kind, from, { mode, until, line })`; the button becomes ■ Stop), tapping its words closes the sheet on the lane there. Takes are invalidated by a different verse too. tools/review.cjs (wrong/silent/noisy lines, late take, line playback, progress on a 2nd take). After a take: % + counts, drag the lane to review; Play modes Voice / Melody / Both (voice is shifted by the recording latency so it lines up with the score). **Listen** plays the melody with the lane + lyrics, no mic.

Tested scores: the bundled Amazing Grace (SATB hymn), Schumann *Dichterliebe* No. 1 (voice + piano, German, long intro — from the OpenSheetMusicDisplay test data), Saltarello `.mxl` (instrumental, no lyrics → note names in the lyric line).

**Future:** a start-point selector (sing from a later line), latency calibration (Bluetooth headphones add 150–250 ms the browser may not report), rhythm/timing scoring.

## Take playback (record page)

The take clock is `mic.ac.currentTime - ctxT0` (not `performance.now()`), so pitch frames and captured audio share one timebase. `recorder-worklet.js` posts the audio-clock time of its first sample plus `Float32Array` chunks; on stop they're stitched into `voice` (peak-normalised gain). Modes: **Voice** (recording), **Notes** (a piano note per detected note), **Both**. Piano notes are shifted earlier by `ANALYSIS_LAG` (50 ms) because a pitch frame describes the trailing 85 ms window — measured lag is ~47 ms. Tap the roll or a chip to move the play cursor. iOS: `navigator.audioSession.type` is set to `playback` for playback (speaker, ignores silent switch) and `play-and-record` before the mic opens. `window.resonateDebug()` (record and sing pages) exposes state for automated tests. Record takes auto-stop at `MAX_TAKE_SEC` (300 s).

Piano: `public/piano/` holds Salamander Grand Piano samples (CC-BY 3.0, attribution in `piano/README.md`), one every minor third A1–C7, trimmed to 3 s mono 64 kbps (~530 KB total). Lazy-loaded and decoded once per AudioContext (`piano.js`); each note uses the nearest sample pitch-shifted via `playbackRate`, starts `ONSET` (12 ms) into the file, and is damped with `RELEASE` when the note ends. Pitch of every sample verified against its name (all within normal piano stretch tuning).

## In-browser OMR (PDF → Song)

Audiveris (Java 25 upstream) runs unmodified-in-spirit inside **CheerpJ 4.2** (WebAssembly JVM, loaded from Leaning Technologies' CDN, Community Edition = personal use). Details in `public/omr/README.md` and `omr-build/README.md`; the short version:

- **Build** (`omr-build/build.sh`): upstream commit `7a36078` + `omr-build/patches/` → compiled with `--release 17` (CheerpJ 4.2 runs ≤ Java 17) → every jar through `StripVolatile.java` → `public/omr/lib/`. Patch 0001 = Java 17 port (pattern switches etc.), 0002 = browser runtime (WebOCR, HOME fallback, web-safe thread pool), 0003 = no AWT in batch (EDT checks only with a GUI), 0004 = lyrics fix (an extender line `pain____` read as a huge-font word made Audiveris drop the whole OCR line — half the syllables; not browser-specific). 0005 = batch robustness: a failed sheet is logged as `Sheet#N failed at STEP: reason` and left out while the other sheets are still exported (`Partial transcription: K of N sheets…`, plus a warning when the first sheet — title/tempo/time signature — is the one missing; before, one bad sheet meant no export at all); every glyph of the music font (156 for Bravura) is checked at startup (outline + a few raster checks; ~1.5 s in CheerpJ, logged as `glyphs checked in N ms`), the font is recreated once if bad, else one ERROR `Music font Bravura unusable: … F_CLEF U+E062 …` naming the failing glyphs and no export; an empty glyph mid-run is also fatal (no silent wrong clefs); `audiveris.fonts.dir` reads font files in place. 0006 = octave clefs: F_CLEF_8VA/8VB were excluded from header clefs ("extremely rare") and the classifier grades octave clefs low (~0.1–0.3 vs ~0.8 for the plain clef), so a low voice's bass-clef-8vb came out an octave high; now the octave variant is used when the classifier proposes it for a glyph extending ≥ ½ interline past the plain clef (below for 8vb, above for 8va) — logged `Staff#N F_CLEF_8VB with an 8 below`. No octave candidates at all on plain clefs of the other test scores (identical output). 0007 = unmarked tuplets: Audiveris only knows "3"/"6" tuplet signs, so the 4th quarter of a quadruplet in 3/4 got no time slot (`No timeOffset for …`) and was dropped with its syllable ("bu-[sy]"); now a chord that comes after a same-staff voice of chords of its duration filling the measure exactly is appended to it (`kept after full voice#N … unmarked tuplet?`), leaving the measure one chord too long for the page side to fix. Only formerly dropped chords are affected (none in the other test scores).
- **Runs in a Web Worker** (`omr-worker.js` hosts CheerpJ + Audiveris + the OCR engine): on the main thread CheerpJ froze the page for up to 11 s at a time. The page side (`omr.js`) renders the PDF and transfers the TIFF.
- **CheerpJ gaps worked around:** no env vars (`user.home=/files`), no GTK/JNA (`sun.java2d.uiScale=1`), no AWT display in a worker (patch 0003), `SynchronousQueue` (VarHandle natives) → `LinkedBlockingQueue` pool under `audiveris.web=true`, reflective access to volatile/final boolean/byte/short/char/float fields (Unsafe natives) → StripVolatile. Java 21 was not available in 4.2; CheerpJ 5.0 (Oct 2026) adds 21/25 — worth trying later.
- **OCR:** `WebOCR.recognizeGray` is a Java `native` implemented in JS (`omr-worker.js` passes it to `cheerpjInit({natives})`); it calls `ocr-engine.js` in the same worker, which drives tesseract.js-core's WebAssembly Tesseract exactly like Audiveris's `TesseractOrder` (legacy engine — needed for word font attributes — PSM 3/6, `SetSourceResolution(70)`, baselines, symbol boxes). Returns URI-encoded tab-separated records.
- **Scanned PDFs:** many PDFs (e.g. Musicnotes scans) are one JBIG2 (or JPEG 2000) image per page. pdf.js 5+ decodes those with WebAssembly modules it loads from `wasmUrl`; without them every page renders blank (0 staves — a user's "Hey, Little Songbird" failed this way before v25). `pdfprep.js` passes `wasmUrl`, `standardFontDataUrl` and `iccUrl` pointing at `omr/pdfjs/{wasm,standard_fonts,iccs}/` (copied from pdfjs-dist 6.5.438; quickjs/cmaps not shipped). Pages with < 0.5% ink are flagged `blank`, and an all-blank PDF gets its own error.
- **The user tests on an iPhone (iOS Safari/WebKit).** Memory is the constraint there: `pdfprep.js` shrinks each page's canvas to 0×0 right after reading it (iOS caps total canvas memory) and `buildTiff` frees each page's pixels once copied (peak ≈ one TIFF, ~9 MB/page). WebKitGTK (`/home/user/xb`: Xvfb + WebKitWebDriver + `wd.mjs`/`wdeval.mjs`, `collect.html` posts the log to `collect-serve.mjs`) is the closest local stand-in.
- **Input:** `pdfprep.js` renders pages with pdf.js at 300 dpi, keeps pages with ≥1 five-line staff (a staff-less page used to make Audiveris fail the whole book; with patch 0005 it'd only be left out), packs them into one gray multi-page TIFF → `/str/score.tif`.
- **OMR clean-ups at import (`omr/fixscore.js`, run by `pdf-import.js` before saving; not in the generic parser):** (1) lyric "verses" with < 15% of the main verse's syllables are OCR artifacts — a lyric line read a bit low gets number 2 (folded into the main verse where it has no syllable: "See, | people get mean…"), footnotes/markings under the staff ("See additional lyrics", "gently") are dropped; (2) if the score has no tempo, the `= NNN` from Audiveris's log line `No beat unit in metronome line "… = 133"` (OCR missed the ♩) becomes a quarter-note `<metronome>` + `<sound tempo>` in the first measure. (3) octave clefs: the engine's evidence for the 8 is borderline and pixel-dependent (on the user's iPhone only 8 of 14 Hades clef changes got it, vs nearly all in sandbox Chromium), so in a single-staff part where the octave was found on ≥ 2 systems and on ≥ ⅓ of that clef's systems, the plain ones get the octave and their notes move an octave, up to the next clef (a singer's staff doesn't switch between a clef and its octave variant; the 8 has never been detected on a plain clef in testing). (4) unmarked tuplets: a voice too long by exactly the duration d of a run of k ≥ 3 consecutive equal elements (notes or rests) lasting d → that run is a k:(k−1) tuplet (quadruplets from patch 0007, triplets whose "3" Audiveris missed): durations scaled, `<time-modification>` added, divisions ×k in that measure and restored after. Without this an overfull measure pushes every later measure late. Songbird: 7 measures, song 456 → 450 beats. (5) missed key signatures (`unifyKeySignatures`): on small staves Audiveris often misses a system's key signature and spells that system in C (Wichita Lineman, F major: the voice had no key for 12 measures and the key flipped F/C every system, B♭→B). Its exporter (`PartwiseBuilder`) writes a `<key>` where a staff's key changes (`number="N"` when a part's staves differ), fifths 0 at a system start where the key is missing after one was known, and **nothing** at the top of a page where it's missing (it forgets keys at each page) — so each staff's key is tracked per staff, a page start without a key counting as "none". Readings per *segment* (system starts + measures where a key was written mid-system): a segment where some staves read a key and others none gets the majority non-zero key (ties → the key read most often); a run of all-"none" segments is filled only next to a segment whose staves disagree (all staves changing together = a real key change, kept); a single staff fills only a gap between two segments in the same key; a key written mid-system is trusted (read from accidentals beyond the header — the staves that wrote it decide that segment, and such a boundary is never evidence of misses). Parts at a constant non-zero key offset from the others on every segment are transposing instruments (Audiveris never writes `<transpose>`) and are judged on their own. Re-keyed notes are respelled in time order (voices interleaved via `<backup>`): no printed `<accidental>` → the key's alteration; printed accidentals carry to later notes of that staff/step/octave in the measure, tie continuations keep their start's pitch. Keys are rewritten where they change and at every page start (idempotent). Synthetic cases in tools/keycases.cjs (C song with a real change to D♭, B♭ clarinet + voice, SATB carry, page-start miss, per-staff key, ties…); real scores other than Wichita are untouched. Changes are logged as `[fix] …`. **Download MusicXML** saves this fixed, titled `.musicxml` (not Audiveris's raw `.mxl`). The Sing page runs `fixOmrScore` again whenever it loads or downloads a song whose `<software>` is Audiveris, so songs saved by older versions get newer fixes without re-converting (the clean-ups are idempotent; the tempo one needs the log, so it only runs at import).
- **One PDF = one score:** Audiveris starts a new score ("movement") at an indented system; Wichita Lineman's indented Coda system made it export `mvt1` (pages 2–3) and `mvt2` (page 4) and the worker kept whichever path it had 300 ms after the first export (phone: page 4 only; desktop: pages 2–3) — with no failed sheet reported. Now `-constant org.audiveris.omr.sheet.ProcessingSwitches.indentations=false` (the switch only drives movement starts in `SystemManager.allocatePages`), and as a safety net the worker collects every `exported to` path (pending while an `Exporting sheet(s)` line has no export yet; done on `Book stored`/`Closing {Score` or 2 s after the last export) and posts `mxls[]`; `pdf-import.js` joins several with `joinMovements` (fixscore.js: measures appended to the part with the same name, else id/position; a missing part gets whole-measure rests; each joined score's first measure gets `<print new-page="yes">` so key/line logic sees the boundary; logged `[fix] N scores (movements) joined`).
- **Title:** best source first — the PDF's own text layer (`pdfprep.js` `textLines`: each page's 8 largest lines that are words — Musicnotes draws the notation with a font, "{} mf", "Ï Ï"; `omr.js` `pdfTitle`: on the pages up to the first music page, the largest line that isn't a publisher line ("Authorized for use by", ©, "Words and Music by"…) and is ≥ 85% of the largest words on its page, so a rejected title doesn't fall to a credit; ALL CAPS takes the mixed-case spelling from another line, e.g. the title page, else Title Case except short words like "SOS"), then the file name when it's clearly a title (Musicnotes `Wichita_Lineman_-_F_Major_-_MN0305807` → "Wichita Lineman", even "1999"; or anything but a camera/scanner default like "Scanned Document 2", "IMG_0042"), then the largest-font page-1 `<credit-words>` (OCR: no publisher lines, no letters-and-digits run together like "Blzmaj7"), else the file name; `movement-title` is rewritten before saving. Scans have no text layer (Songbird → file name). tools/titlecases.cjs.
- **Tempo from the PDF's text:** `pdfprep.js` `tempoMark` finds "= 104" in a page's text (the number is text; the note is a music-font glyph — read when it's SMuFL U+ECA3/ECA5/ECA7 (+ECB7 dot) or Unicode ♩♪𝅗𝅥, else unknown; a range "= 92-96" takes the first number); `omr.js` returns the first music page's as `res.tempo` ({bpm, unit, dotted}); `restoreTempo` (fixscore) prefers it — added unless the first measure already has a tempo (a later mark the engine read doesn't block it) — over Audiveris's log line (OCR digits, position unknown: only used when the score has no tempo at all). Unknown beat unit → the meter's usual one: dotted quarter in 6/8, 9/8, 12/8, half in cut time, else quarter (`<sound tempo>` in quarters: ♩. = 66 → 99). The user's phone conversion of Wichita Lineman missed "♩ = 104" and played at the default 90.
- **Jars:** GUI-only libraries are not shipped (itext, jfreechart, github-api, jackson, jgoodies, commonmark, jna — `SKIP` in build.sh / `JARS` in omr.js): CheerpJ reads each classpath jar's index (~0.4 MB) up front. Verified identical output without them.
- **Rendering:** pages are binarized, counting pixels darker than ~80% white as ink (`< 200000` in `pdfprep.js`). pdf.js anti-aliasing left gray glyph edges that cut lyric recognition from ~44% to ~15%; the dark-leaning cut (slightly bold glyphs) beat a 50% cut on all four test scores (Killing Me Softly 87% → 98% of syllables) with identical notes.
- **CheerpJ 4.2 JIT bug (fixed in the build, v24):** once warm, CheerpJ 4.2/4.3 miscompile code that allocates a 2-D primitive array in one shot (`new double[m][n]`, bytecode `multianewarray`) and fills it element by element — Jama's `Matrix.getArrayCopy` — so every circle fit behind slur/tie detection threw "Matrix is singular" after ~70 calls: page 1 got fewer slurs, pages 2+ got **none** (ties lost → held notes played twice on the Sing page, tie curves misread as fermatas). `StripVolatile.java` now also rewrites every `multianewarray` of a 2-D primitive array (178 sites across the jars) into a call to a generated `cheerpjfix/Arrays2D` helper that allocates row by row; verified natively with `-Xverify:all` (identical output) and in the browser (slurs per page = native, ties in 44 measures = native). Probe tools: `/home/user/cjtest/jama` (`LuProbe`, `JamaProbe`). CheerpJ 5.0 doesn't have the bug.
- **Checking a conversion beyond notes:** `score_omr.py` compares notes one by one and can't see ties; also compare the Sing parser's merged note count with the hand transcription's (250 for the test score) and the measures with `<tie>` against native Audiveris (44). Per-sheet "Slurs: N" log lines vs a native run catch engine regressions.
- **Exit:** `omr.js` reads the `.mxl` as soon as Audiveris logs "exported to …" (CheerpJ threads parked in a queue don't wake on interrupt, so executor shutdown would sit out its grace delay; `graceDelay=1` too).
- **Accuracy on the test score** (vs a 3-way reconciled hand transcription, 311 sung notes): notes 100% found, pitch 99.7%, rhythm 100%, melody notes after merging holds 250 = hand transcription's 250 (v24; 300 before the JIT fix), lyric syllables 95% in the browser (98% native Audiveris; was 37% before patch 0004 + the darker binarization — the rest are one-letter OCR slips like `ly`→`y`). Synthetic scores (Amazing Grace, Oh Susanna, Greensleeves, rendered with Verovio) are 93–100% lyrics, 100% notes. Audiveris also drops "rhythm-slash" multi-bar rests. (The Sing page now unfolds repeats, so a converted song's melody-note count in performance order is larger than the written 250.)
- **First-run download** ≈ 60 MB (CheerpJ runtime ~24 MB from its CDN, jars ~18 MB, OCR ~16 MB); ~11 min for 6 pages in desktop Chromium.
- **One conversion per page load** (Audiveris global state); "Convert another" reloads.
- **One conversion per browser, clean slate each time:** CheerpJ's only writable mount, `/files` (also `java.io.tmpdir`, not overridable), is one IndexedDB database per site (`cjFS_/files/`). Two engines at once (two tabs) corrupt it, and since the worker is killed, Java never deletes its temp files (~2 MB per run). So `omr-worker.js` takes a Web Lock (`resonate-omr-engine`; a second tab gets a clear "already running in another tab" error) and deletes that database before starting.
- **Music font from memory:** `omr-worker.js` fetches `omr/fonts/Bravura.otf` (copied out of the jar by build.sh) into `/str/Bravura.otf` and sets `audiveris.fonts.dir=/str`, instead of `Font.createFont` copying it into IndexedDB.
- **The 0x0 symbol crash (Nov 2026, one user report, not reproduced):** every sheet failed at HEADERS with `Width (0) and height (0) cannot be <= 0` — Bravura was created but FreeType (wasm, in CheerpJ's natives) returned empty glyph outlines, which OpenJDK reports silently. Same PDF works in headless Chromium and WebKitGTK 2.52 here; all 670 symbols in all 6 music fonts render identically to native. Patch 0005 makes it fail loudly with a browser hint; the log now starts with the user agent / threads / RAM, and Details has **Copy log** — ask for that log if it recurs.
- **Failures surface in the UI:** `omr.js` turns `Sheet#N failed…` lines into `failed: [{page, step, reason}]` (result card lists pages left out) and maps "font unusable" / "no page read" to plain-language errors.
- **Speed:** on the user's iPhone ~5 min for the 9-page Songbird scan (~30 s/page); the sandbox's headless Chromium is much slower (~2 min/page) — don't base user-facing estimates on it. ~2 min/page in sandbox Chromium once warm (it was ~1 min/page while slurs were silently broken, see below); phones slower. Step timeout raised to 2 h. CheerpJ 5.0 was tried: correct, but 17½ min for the same 6 pages (its BEAMS step ran ~5× slower).
- **Never commit test scores** (e.g. the user's licensed Musicnotes PDF) — test from outside the repo (`/home/user/sitetest` symlinks `public/` as `/resonate/`).
