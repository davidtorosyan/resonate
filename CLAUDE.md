# Resonate

A vocal pitch + waveform web app served over LAN so it can be used from a phone. Sing into the mic, see the note name, cents-off, volume, and live waveform.

## Deploy (primary workflow)

Push to `main` → `.github/workflows/deploy.yml` publishes `public/` to the `gh-pages` branch → live on GitHub Pages (HTTPS, so the mic works on a phone with no cert hassle). This is the normal iteration loop: make the change, bump the version badge, push to `main`, tell the user when the deploy finishes. The local server below is only for offline testing.

## UI principles (standing — the user's direction, see docs/ROADMAP.md)

- **Feedback coaches; it doesn't grade.** This is for learning to sing, not a game. Keep every number (scores, cents, timing) in the data (history, sync, the AI coach), but don't put grade-like numbers in front of the singer: no percentages after a line or a take, no scoreboard counts, no red "fail" marks. Lead with what went well, then at most a few concrete things to try, each with a way to hear it. Build this into the data model (observations with a tone), not as a skin over scores.
- **Few words.** Don't explain what the user just did or what a control obviously does. Show the facts that matter compactly (e.g. a song's range before → after a key change, not a paragraph about fitting a profile). Prefer a short label, a symbol or a number with a unit over a sentence.
- **Everything works signed out.** GitHub Pages is the host; signing in (planned) only adds cloud sync and the AI/MCP connection.

## Run (local, optional)

```
cd C:\Data\Claude\resonate
npm start
```

Server prints both HTTP (port 3000) and HTTPS (port 3443) URLs for localhost and every detected LAN IPv4. **In practice the port that matters is 3443 (HTTPS)** — that's the one used from a phone, because `getUserMedia` is blocked on insecure origins for any non-localhost host. Port 3000 (HTTP) is only useful for localhost testing. There's no auto-reload; restart the node process to pick up `server.js` changes. Frontend changes (`public/`) just need a browser refresh.

**Which Network URL to give a phone:** the banner lists *every* IPv4, including virtual adapters — Hyper-V's "vEthernet (Default Switch)" (`172.x`) and VirtualBox host-only (`192.168.56.x`). A phone can't reach those. Pick the **Wi-Fi adapter's** IP (the one on the same subnet as the phone).

**Restarting:** `server.js` calls `listen()` with no `error` handler, so if an instance is already running, `npm start` prints the banner and *then* crashes hard with `EADDRINUSE` on 3000. A running instance holds both 3000 and 3443 — so this error also means "it's already up." To restart cleanly, kill the existing `node` process first (`Get-Process node | Stop-Process`).

## Version marker

`index.html` shows a `v<N>` badge in the top-right of the header (`#version`, purple). It exists so you can confirm a frontend change actually reached the phone — bump the number, refresh, check the badge. **To bump, run `node bump.mjs <N>`** (repo root): it sets the badge on every page and puts `?v=<N>` on every local script/module address (`<script src>`, `import … from`, `import()`, `new Worker()`, `addModule()`, `importScripts()`), so a new page only ever loads that version's code. GitHub Pages lets browsers reuse each file for 10 minutes (`max-age=600`), one module at a time: v54's sing.js with a cached v53 library.js failed with "does not provide an export named 'saveClean'" and the Sing page showed nothing but Amazing Grace. A new module must be imported with the `?v=` suffix too (the script adds it to any `.js` import). The song library's clean-up cache is keyed by the badge as well. If the badge doesn't change after a refresh, the phone is serving a cached `index.html` — hard-refresh / pull-to-refresh.

## Stack

- Node 21+, ESM, Express 4, `selfsigned` for cert generation
- Vanilla HTML/CSS/JS frontend, no build step, no framework
- Web Audio API (`AnalyserNode`, fftSize 4096) for capture; YIN for pitch detection; Canvas 2D for the waveform

## HTTPS / self-signed cert

Generated on first run to `certs/cert.pem` and `certs/key.pem`. SAN includes `localhost` and every IPv4 present at generation time.

**If the LAN IP changes** (router lease, network switch), the cert won't cover the new IP — delete `certs/` and restart to regenerate.

Browsers warn ("not private") because the cert isn't CA-signed. On iOS Safari: "Show Details" → "visit this website".

## Windows firewall

If the phone can't reach the server, this is the most likely cause. Allow inbound on 3000 and 3443.

## Pitch detection (`public/app.js`)

YIN algorithm (de Cheveigné & Kawahara, 2002). Chosen over FFT peak-picking because YIN avoids the octave errors that vocals trigger. Inner loop is bounded to `tau ∈ [minTau, maxTau]` covering only the vocal range (~50–1100 Hz) — keeps it cheap enough for phones.

`detectPitch` sets `halfN = buf.length - maxTau` so the autocorrelation uses every sample the largest lag will allow, instead of the standard `buf.length / 2`. This is what makes low-pitch detection viable at fftSize 4096; reverting halfN to `buf.length >> 1` halves the cycles available for sub-100 Hz pitches and the dip stops triggering. The threshold for accepting a YIN dip is 0.2 (paper suggests 0.1–0.15; relaxed because low-fundamental vocals often don't dip below 0.15).

Mic constraints disable `echoCancellation`, `noiseSuppression`, and `autoGainControl`. Browser defaults distort pitch and amplitude in ways that break detection and meter scaling.

## Locked-note display logic

The shown note isn't `round(current pitch)` — that flickers when vibrato lands near a semitone boundary and lags badly when the user intentionally jumps to a new note. Instead:

- `lockedNote` is a single integer MIDI we currently display.
- Cents number + needle = long-window median (1.5 s) compared to `lockedNote`.
- Each frame, the **short-window median** (300 ms) is compared to `lockedNote`. If it's >50¢ off, an off-note timer starts and the note dims (`data-onnote="false"`).
- If the short median stays >50¢ off for **250 ms**, we re-lock to `round(short median)` and trim history older than the short window so the long median resnaps.

Net feel: holding a note is rock-stable; intentional jumps cause a brief dim then a clean snap.

## Tunable constants (top of `public/app.js`)

| const | default | effect |
|---|---|---|
| `PITCH_WINDOW_MS` | 1500 | long smoothing — bigger = more stable cents number, slower settle |
| `SWITCH_WINDOW_MS` | 300 | live-pitch window — smaller = more reactive but jitterier |
| `SWITCH_DELAY_MS` | 250 | grace period before snapping to a new note |
| `MIN_RMS` | 0.012 | loudness gate — raise if room noise produces false readings |
| `MIN_CLARITY` | 0.80 | YIN clarity threshold — raise for stricter readings |
| `MIN_FREQ` / `MAX_FREQ` | 50 / 1100 Hz | vocal range bound for YIN; sets `minTau`/`maxTau` |

## Volume meter

Maps RMS → bar width via `(dB + 55) * 2`, clamped 0–100%. Roughly −55 dB empty, 0 dB full. If the bar sits too full or too empty for your mic gain, adjust the `+55` constant in `updateVolumeMeter()`.

## Record page note segmentation (`public/record.js`)

Per frame: YIN pitch (`pitch.js`, same settings as the tuner) → median over `SMOOTH_MS` (100 ms). A note continues while the smoothed pitch stays within 50¢ of the note's median; it splits when the pitch sits >50¢ away for `SPLIT_MS` (80 ms), and ends on an unvoiced gap ≥ `GAP_MS` (70 ms). Notes shorter than `MIN_NOTE_MS` (60 ms) are dropped. Voicing also requires the RMS of the newest `TAIL_SAMPLES` (1024, ~21 ms) to pass `MIN_RMS` — the full 4096-sample window smears short gaps, which otherwise merges repeated same-pitch notes. No beat grid yet; times are seconds.

## Sing mode (karaoke, `sing.js`)

The **score is the clock** (an earlier version aligned sung notes to the score ignoring rhythm — dropped: wrong notes leave nothing reliable to align on).

**Parsing (`musicxml.js`):** picks the part+voice with the most lyric syllables (the melody — e.g. soprano of an SATB hymn). Tracks position across all voices (`backup`/`forward`) so each note gets an `onset` and `dur` in quarter notes; measure starts in `measures` (a short first measure = pickup). Syllables printed under the melody's staff but attached to another voice there (recognition gives a syllable to the chord nearest the words — in a piano part often the accompaniment under the tune: The Longest Time's "For the long-est" came out "For ‿ long ‿") move to the melody note starting at the same moment, when it has none of its own for that verse; a hymn's identical words under every voice are untouched. Keeps the highest note of chords, skips grace/cue notes, merges ties — and also merges the first note of a new system/page (`<print new-system|new-page>`) into the previous sung note when it has the same pitch, no syllable in any verse and no rest between: a tie split by a line break, which OMR (Audiveris) often loses across pages; rests become gaps (and `restBefore`). Tempo = first `<sound tempo>` or `<metronome>` (its per-minute's first number: "about 76"; default 90 if none), time signature from the first `<time>`, and every measure's meter in `score.meters` (kept through unfolding; v52) — the Sing page counts in, clicks and taps in the meter where the singing starts (`meterAt`; `countInMeter`: the entry bar's own meter, or the next bar's when the entry bar is a pickup — one meter for the count-in's beats, pace and accents, v53), so Piano Man's 4/4 "Freely" intro doesn't give its 3/4 song a 5-click 4/4 count-in. Lyrics per verse; a note with no syllable after a sung one is a melisma continuation (`‿`). **Repeats are followed** (`readStructure` → `performanceOrder` → `unfold`): barlines (repeats with `times`) and directions (segno/coda signs, `<sound>` segno/dalsegno/dacapo/tocoda/coda/fine, words "D.S."/"D.C."/"To Coda"/"Fine") are read from every part, `<ending>` brackets from the top part only (they're drawn above the system; Audiveris reads piano 8va lines as endings on lower staves — Wichita's piano had three); ending numbers "1, 2" / "1.2.3." are lists, "1-3" and Audiveris's "1,,3" (its export of a printed "1.-3.") ranges. A repeat goes back to the last forward repeat (or the start, or just after the previous repeat) and plays `times` times, or one more than its ending's highest number, and — when no D.S./D.C. comes back — at least as many times as its section has verses (max 8); an ending plays on its numbered passes, one past all its numbers that doesn't repeat is the final ending; a 1st ending that stops just before its repeat sign runs to it (Wichita: Audiveris put "1." on m21 only, the repeat is at m22); after a D.S./D.C. repeats aren't retaken, first endings are skipped, To Coda jumps to the Coda, Fine ends; D.S. with no segno found is ignored. Each played measure gets a verse *pass*: the pass of the repeat it's in, 1 for new music after a repeat or a final ending, after a D.S./D.C. one more than the times its target was sung. A note sings verse k if it has it; after the last verse-k word of its measure, the latest verse it has when the following music has no verse k (a refrain printed once under line 1); in the last measure before a repeat sign, the next verse's word (a pickup printed on line 2 in a 1st ending); a measure with no verse k at all sings the latest verse it has. The chosen syllable becomes verse "1" (`score.verses` = ["1"], so the verse menu disappears) and `score.unfolded` = {written, played, passes} — unless the song has stacked verses no pass reaches (a hymn with a repeated refrain): then the written order and the verse menu stay. A note tied across a jump (into a 1st ending, over To Coda) is cut at the jump; a note right after a jump starts a new lyric line only if a rest precedes it (Wichita's "small va-ca-tion" stays on one line). Wichita: "…small va-" → back to the verse for "-cation, but it don't look like rain" (pass 2, refrain words reused) → 2nd ending → Coda (its repeat twice). Killing Me Softly: 69 written → 107 played measures (verse/chorus twice, bridge, chorus repeat); only verse-1 words in the score, so pass 2 repeats them. tools/repeatcases.cjs (20 cases: endings, AABB, intro vamp, no forward sign, D.S./D.C., hymn, refrain pickup, 1st-ending pickup, tie cut), tools/flow.cjs (a song's lyric lines in performance order). Lyric text cleanup: a performance direction read as a syllable ("sim.", "simile", "cresc.", "rit."…) is dropped; verse numbers stripped, `I 'm` (often with a non-breaking space) → `I'm`. `lyricLines()` splits a verse into display lines at rests and line-ending punctuation. Title falls back to the largest-font `<credit-words>`.

**Session:** one AudioContext for mic + guide so clocks match. Count-in = one bar (+ the missing beats of a pickup bar, fractional when the pickup isn't whole beats — an eighth pickup in 4/4 is 7½: the pickup lands on the "and" of 4; rounding used to put the song half a beat late against its own count-in, v58) of clicks, in the *felt* beat (`feltBeat`: a dotted quarter in 6/8, 9/8, 12/8, else the meter's unit); the guide's clicks (`beatGrid`) too, and a pickup bar (written measure 0, `score.measureOf`, and its replays) counts back from its barline; `songT0` = song time 0 on the audio clock. The click (`piano.js` `clickWave`/`playClick`) is a seeded 30 ms noise burst, 4th-order high-passed at 2.5 kHz (accent 3.5 kHz) — the same waveform every time, −50 dB below 1 kHz — as loud (RMS) as the old band-passed one. The count-in number (status line, Perform's big number) changes on each click (`countInLeft`); a loop round on a line in the song's pickup bar gets the pickup's missing beats too (v60). tools/countin.cjs. Guide while singing: **click** (default — a noise burst, so speaker bleed into the mic isn't read as pitch), **melody** (piano; use headphones or the mic grades the piano), **none**. Settings: verse, transpose, tempo (50–125% of the score's), persisted in `localStorage` (`resonate.sing.*`). **Transpose** (−12…+12 semitones, remembered per song in `resonate.sing.keys`; the old global `resonate.sing.transpose` is migrated to the song that was open) works like a notation editor: `transposeKey` (music.js) picks the new key with the fewest accidentals (ties → flats) and the interval's size in letters, and `spellTransposed` moves each note's *written* spelling (the parser keeps `letter`/`alter`) by that interval — C minor +2 = D minor, A♭→B♭, leading-tone B→C♯ (double sharps/flats respelled). Options name the key they land in ("Key Cm", "+2 Dm", "−12 Cm 8vb"; major/minor from `<mode>`, else the final chord's bass (`score.finalBass`, lowest note of the last measure with notes, all parts) or the melody's last note when it's one of the two tonics the signature allows, else the tonic the melody dwells on — Wichita Lineman ends on B♭maj7 and its melody dwells on D, but the melody ends on F: F major; PDF → Song also writes `<mode>` from a Musicnotes file name's "…_F_Major_…"). Chips, the target readout and lyric-less note names use these spellings; the summary shows the transposed range (lowest–highest). Pitch itself (targets, guide, Listen, grading) is just `midi + shift`. **With a voice profile the transpose menu shows what fits** (`fitOptions`, fit.js): every whole-song shift −24…+24 plus, for each key s (−6…+5), its best *split* — one key for the song, whole phrases moved by their own octaves (phrases split at rests and at leaps > an octave — singers handing over without a rest), chosen exactly by DP per key — when the split beats singing that key whole. Groups: **Fits <name> (C3–E4)** (< 2% of the sung beats outside the comfortable range, none beyond the limits), **Close** (< 15% out, < 2% beyond; or "Closest for <name>" when nothing fits), then **Other keys** (−12…+12 whole), and for a song whose best option is a split (a duet on one staff), **Other keys, parts split** (each key's split, e.g. its own key) first. Sorted by cost: beat·semitones outside the comfortable range 1/semitone, beyond the limits +4, within 2 semitones of a comfortable edge 0.25, changing octave between phrases 24, moving at all 0.02 per beat·semitone. Labels name the landing key and mark the song's own key ("−12 A♭ · same key", "−10 B♭", splits as "+17 / −7 Fm · 5% out") so you can choose staying in key over the closest fit. Values: a number (whole-song shift) or `"fit:s"` (key s split, re-solved on load with `fitKey` so it follows the profile); v32's single `"fit"` is converted to the option `fitToRange` picks. Under the song bar (`showFitMsg`, whenever the key moved or there's a voice range): the song's range as written → as sung, and the comfortable range — "E♭4–E♭5 → D3–D4 · Dave C3–E4 ✓" (or "· 39% out"); without a range and with "Fit my range…", a "Set your range" link (v58; it was a paragraph about phrases and octaves). Without a profile range the first option is "Fit my range…" (links to the Voice page). Songbird (Hades F1–C3, Eurydice G3–B♭4) for a baritone C3–E4: closest Fm split +17/−7 (5% out); its own key Cm +24/+12/−12 (7% out). Notes get per-note shifts (`shifts`); a take's grades are kept only while `shiftSig` and tempo match.

**Tempo & tapped timing (v49, `timing.js`):** every time on the page comes from `qToT(q)` (quarters in performance order → song seconds; notes keep `q`/`dq`): the score tempo × `rate`, or, when the song has a timing tapped along with a recording and it's chosen, that timing ÷ `rate`. The tempo menu: *Recording's timing (tapped)* — Tapped, · 90%, · 80%, · 70% (`m:<rate>`) — then *Steady tempo* (`r:<rate>`; a tapped tempo shows as "♩=97 (yours)"), then *Set the tempo*: **Type a tempo…** (v51: a prompt for quarter notes per minute, 20–400, rounded; kept as this song's own `bpm` like a tapped tempo — e.g. Piano Man's "𝅗𝅥. = 58" imported as ♩=58, really ♩=174), **Tap the beat…** (pad, median of the last ≤ 12 intervals after 4 taps, a pause > 2.5 s starts over; the meter's beat — dotted quarter in 6/8, 9/8, 12/8 — sets `rate` exactly) and **Tap along with a recording…** (play the song anywhere — the page makes no sound and suspends its playback context, and the first-tap unlock skips these screens so other apps' audio isn't interrupted — and tap the pad on each syllable (or each line's start) as it's sung; ◀ ▶ picks the starting line, ↶ undoes; the next syllable is underlined). Taps → knots [q, t] (a tap < 60 ms after the last is ignored before it uses up a syllable; `knotsFromTaps` also drops out-of-order ones; `splitPauses`: a gap > 4× the median pace and > 3 s — leaving to restart the music — is left out, each run merged on its own, and the message says so) → segments [q, s/quarter] merged into the song's map (`mergeKnots`: only the tapped span is replaced, paces rounded to 0.1 ms/q) → `makeTiming` (before/after the tapped span and in untapped gaps: the map's average pace; time 0 at q 0). Stored per song (`resonate.sing.timing` = { songId: { sig: note count — verses with the same music share it, segs, use, bpm } }; `bpm` = a tempo tapped for this song, so it isn't applied to other songs — the global `resonate.sing.rate` only holds the menu's percentages); saving sets rate 1 and the map on; *Forget the tapped timing* removes it. Clicks (`beatGrid`), Listen, the lane's bar lines, entry bar, count-ins (pace over the next two bars from the start, `beatSecAt` — one stretched pickup doesn't set it; the count-in number never exceeds the clicks) and grading all follow it. A take's grades hold only for the timing it was sung to (`take.timing` = `timingSig()`). Summary: "TAPPED TIMING ♩≈58". tools/timingcases.mjs (node), tools/taptiming.cjs (browser: tap tempo 120, tap-along 25% slower with a held word → notes within 3 ms of the taps, 90%, reload, forget).

**Entry bar:** the count-in, clicks, lane and Listen start at the bar containing the first sung note (`entryIdx`/`entryT`), so songs with an instrumental intro (e.g. art songs) don't make you wait through it. `songT0` is offset so song time stays absolute.

**Frame timing:** `frameT = songT − ANALYSIS_LAG − latency`, where `latency = outputLatency (or baseLatency) + INPUT_LATENCY (20 ms)` — the singer follows what they hear late, the mic hears them late, and a pitch frame lags its audio.

**Grading (`grade.js`, v44):** each note's slot may move — its start up to `MAX_SHIFT` (0.24 s) either way in 30 ms steps, chosen for the whole take at once by dynamic programming over the notes (they stay in order, a moved slot keeps ≥ 40% of its length; moving costs `MOVE` 0.15/s, changing the shift between joined notes `DRIFT` 0.1/s, across a rest 0.03/s), cost = the *time* in the whole slot not within 50¢ (additive: each frame is charged once whichever slot it's in, so moving a boundary only pays when frames really match the note they move into — v47; the first version weighted by note length × miss share, which let scoops and silences be spread over a longer neighbour: a correct short note after a scoop went "off", a silent repeated note borrowed its same-pitch neighbour's ring-over and went "good"), plus time the note was sung in the rest *before* it (early entries; a note rung on into the rest after it is phrasing and free — charging that pushed the last note +0.24 late and turned the note before it "off"). For a note after a rest, up to 2 semitones flat counts as on the note when *aligning* (scooped entries aren't "late"; silence still is). Frames are looked up 2×`MAX_SHIFT` around each note (rest regions not clipped). A rusher's right notes used to land in the neighbouring slot and be marked off: a simulated singer 150 ms early on Amazing Grace scored 62% (9 off, 3 missed) before, 97% after. A note is then judged on its moved slot minus the grace (`min(120 ms, 25%)`): voiced ≥ 35% → median octave-folded deviation ≤25¢ good, ≤50¢ close (ok), else off; else loud-but-unpitched (rms ≥ `loudGate`: `MIN_RMS` or 2.5× the quietest quarter second of the take's median rms, whichever is higher — v47, so a fan or traffic doesn't make skipped notes "unclear") + voiced ≥ 50% → **unclear** ("couldn't hear the pitch" — not counted in the %; dotted chip, light blue), else missed. Grades carry `shift` (s, − = early), `from`/`to` (the moved slot). `hit` = share of the slot's frames within 50¢; the take's % (`takeScore`) = duration-weighted mean `hit` over notes not unsung/unclear. Summary adds "· N UNCLEAR" and "· EARLY/LATE ~.15 S" (`timingTendency`: median shift of in-tune notes, shown from 80 ms). During the take a note is graded alone (`gradeLive`, its best shift) once frames pass its end + `MAX_SHIFT`; at the end `gradeTake` regrades all and the pitch line is recoloured against each frame's matched note. Lane: a short line above a bar shows where you sang it when ≥ 80 ms early/late. Frames keep `rms`. Notes after Stop (first half not reached) are *unsung*; a reached note whose squeezed slot holds < 2 frames after the grace is judged on its whole span, else its written slot (never unsung). Octave sung is reported (8vb/8va). tools/gradecases.mjs (node: in time, early, late, drifting, silent, unclear, wrong, flat, octave, stopped, too early, 450-note speed ~40 ms), tools/gradeearly.cjs (browser, simulated singer with OFFSET and NOISE notes).

**Rhythm (v58, `rhythm.js`; design and reviews in docs/ROADMAP.md §1):** when each note came in, from the take's recording (no speech recognition). `capture.js` now records loop rounds too (`keepSeconds`: just the count-in; `finish()` disconnects the node and closes its port so rounds don't pile up) and streams every chunk (`onChunk`) into `makeFeatures` during the take: every 5 ms the energy in 80–450 Hz (lo), 500–2500 Hz (mid: vowel formants — the syllable's beat is felt at its vowel, consonants come before it) and ≥ 3 kHz (hi), 4th-order bands. At Stop: `findClicks` finds the count-in clicks in the recording with a matched filter (each click's correlation lined up on its scheduled time and summed, lags up to just under a beat so the next identical click can't alias; earliest clear peak, ≥ 25× the summed correlation's median — mic hiss alone reached ~14 and passed the first gate of 6, so headphone takes got a fake ~0 ms "calibration", v60; ≥ half the clicks agree within 4 ms; a round trip ≤ 3 ms is rejected) → the real round trip `rt` (output + input latency) and `coupling` (how loud the speaker is in the mic; found down to ~1% — an iPhone's quiet in-call output). With it the take's frames move by `latency − rt`, `take.latency = rt`, the voice playback is aligned with `rt`, then `gradeFinal` runs — one clock. `findOnsets`: vowel-band envelope over 20 ms windows (a bass's period), noise floor = the quiet between phrases (or 20 dB under the median when the recording is sung all through); attacks = a ≥ 6 dB rise in ~40 ms that holds ≥ 35 ms, timed where it first gets within 9 dB of the vowel's level (past an m/n/l/w hum) − 10 ms; glides = a two-level step fit of the pitch frames between two joined notes of different pitch (validated: ≥ 3 frames each side, each side near its note, much better than one level — else the note wasn't sung); voicing starts (weak). ## Take playback (record page)

The take clock is `mic.ac.currentTime - ctxT0` (not `performance.now()`), so pitch frames and captured audio share one timebase. `recorder-worklet.js` posts the audio-clock time of its first sample plus `Float32Array` chunks; on stop they're stitched into `voice` (peak-normalised gain). Modes: **Voice** (recording), **Notes** (a piano note per detected note), **Both**. Piano notes are shifted earlier by `ANALYSIS_LAG` (50 ms) because a pitch frame describes the trailing 85 ms window — measured lag is ~47 ms. Tap the roll or a chip to move the play cursor. iOS: `navigator.audioSession.type` is set to `playback` for playback (speaker, ignores silent switch) and `play-and-record` before the mic opens. `window.resonateDebug()` (record and sing pages) exposes state for automated tests. Record takes auto-stop at `MAX_TAKE_SEC` (300 s).

Piano: `public/piano/` holds Salamander Grand Piano samples (CC-BY 3.0, attribution in `piano/README.md`), one every minor third A1–C7, trimmed to 3 s mono 64 kbps (~530 KB total). Lazy-loaded (the mp3s kept per page, `sampleFile`) and decoded once per AudioContext (`piano.js`), played a few seconds ahead at a time (`scheduleAhead`, see Sing → Scheduling ahead); each note uses the nearest sample pitch-shifted via `playbackRate`, starts `ONSET` (12 ms) into the file, and is damped with `RELEASE` when the note ends. Pitch of every sample verified against its name (all within normal piano stretch tuning).

## In-browser OMR (PDF → Song)

Audiveris (Java 25 upstream) runs unmodified-in-spirit inside **CheerpJ 4.2** (WebAssembly JVM, loaded from Leaning Technologies' CDN, Community Edition = personal use). Details in `public/omr/README.md` and `omr-build/README.md`; the short version:

- **Build** (`omr-build/build.sh`): upstream commit `7a36078` + `omr-build/patches/` → compiled with `--release 17` (CheerpJ 4.2 runs ≤ Java 17) → every jar through `StripVolatile.java` → `public/omr/lib/`. Patch 0001 = Java 17 port (pattern switches etc.), 0002 = browser runtime (WebOCR, HOME fallback, web-safe thread pool), 0003 = no AWT in batch (EDT checks only with a GUI), 0004 = lyrics fix (an extender line `pain____` read as a huge-font word made Audiveris drop the whole OCR line — half the syllables; not browser-specific). 0005 = batch robustness: a failed sheet is logged as `Sheet#N failed at STEP: reason` and left out while the other sheets are still exported (`Partial transcription: K of N sheets…`, plus a warning when the first sheet — title/tempo/time signature — is the one missing; before, one bad sheet meant no export at all); every glyph of the music font (156 for Bravura) is checked at startup (outline + a few raster checks; ~1.5 s in CheerpJ, logged as `glyphs checked in N ms`), the font is recreated once if bad, else one ERROR `Music font Bravura unusable: … F_CLEF U+E062 …` naming the failing glyphs and no export; an empty glyph mid-run is also fatal (no silent wrong clefs); `audiveris.fonts.dir` reads font files in place. 0006 = octave clefs: F_CLEF_8VA/8VB were excluded from header clefs ("extremely rare") and the classifier grades octave clefs low (~0.1–0.3 vs ~0.8 for the plain clef), so a low voice's bass-clef-8vb came out an octave high; now the octave variant is used when the classifier proposes it for a glyph extending ≥ ½ interline past the plain clef (below for 8vb, above for 8va) — logged `Staff#N F_CLEF_8VB with an 8 below`. No octave candidates at all on plain clefs of the other test scores (identical output). 0007 = unmarked tuplets: Audiveris only knows "3"/"6" tuplet signs, so the 4th quarter of a quadruplet in 3/4 got no time slot (`No timeOffset for …`) and was dropped with its syllable ("bu-[sy]"); now a chord that comes after a same-staff voice of chords of its duration filling the measure exactly is appended to it (`kept after full voice#N … unmarked tuplet?`), leaving the measure one chord too long for the page side to fix. Only formerly dropped chords are affected (none in the other test scores). 0008 = lyrics between the staves of a multi-staff part: `TextRole.guess` only ever made text between two staves of the *same* part a Direction, so a piano/vocal arrangement with the tune in the piano's right hand and the words between the piano staves (Musicnotes' The Longest Time) came out with 1 syllable in 326 notes; now a non-italic line of ≥ 2 words with vowels there is Lyrics ("sim.", "8va bassa throughout" are italic and stay directions), mapped to the staff above as before (`mapLyricLines`: same part → above). A/B on seven scores (Piano Man, Wichita, Killing Me Softly, Songbird, Amazing Grace, Greensleeves, Oh Susanna): the sung melody and its words identical; 1–2 stray syllables appear in Piano Man's and Songbird's piano parts, which the parser never picks.
- **Runs in a Web Worker** (`omr-worker.js` hosts CheerpJ + Audiveris + the OCR engine): on the main thread CheerpJ froze the page for up to 11 s at a time. The page side (`omr.js`) renders the PDF and transfers the TIFF.
- **CheerpJ gaps worked around:** no env vars (`user.home=/files`), no GTK/JNA (`sun.java2d.uiScale=1`), no AWT display in a worker (patch 0003), `SynchronousQueue` (VarHandle natives) → `LinkedBlockingQueue` pool under `audiveris.web=true`, reflective access to volatile/final boolean/byte/short/char/float fields (Unsafe natives) → StripVolatile. Java 21 was not available in 4.2; CheerpJ 5.0 (Oct 2026) adds 21/25 — worth trying later.
- **OCR:** `WebOCR.recognizeGray` is a Java `native` implemented in JS (`omr-worker.js` passes it to `cheerpjInit({natives})`); it calls `ocr-engine.js` in the same worker, which drives tesseract.js-core's WebAssembly Tesseract exactly like Audiveris's `TesseractOrder` (legacy engine — needed for word font attributes — PSM 3/6, `SetSourceResolution(70)`, baselines, symbol boxes). Returns URI-encoded tab-separated records.
- **Scanned PDFs:** many PDFs (e.g. Musicnotes scans) are one JBIG2 (or JPEG 2000) image per page. pdf.js 5+ decodes those with WebAssembly modules it loads from `wasmUrl`; without them every page renders blank (0 staves — a user's "Hey, Little Songbird" failed this way before v25). `pdfprep.js` passes `wasmUrl`, `standardFontDataUrl` and `iccUrl` pointing at `omr/pdfjs/{wasm,standard_fonts,iccs}/` (copied from pdfjs-dist 6.5.438; quickjs/cmaps not shipped). Pages with < 0.5% ink are flagged `blank`, and an all-blank PDF gets its own error.
- **The user tests on an iPhone (iOS Safari/WebKit).** Memory is the constraint there: `pdfprep.js` shrinks each page's canvas to 0×0 right after reading it (iOS caps total canvas memory) and `buildTiff` frees each page's pixels once copied (peak ≈ one TIFF, ~9 MB/page). WebKitGTK (`/home/user/xb`: Xvfb + WebKitWebDriver + `wd.mjs`/`wdeval.mjs`, `collect.html` posts the log to `collect-serve.mjs`) is the closest local stand-in.
- **Input:** `pdfprep.js` renders pages with pdf.js at 300 dpi, keeps pages with ≥1 five-line staff (a staff-less page used to make Audiveris fail the whole book; with patch 0005 it'd only be left out), packs them into one gray multi-page TIFF → `/str/score.tif`.
- **OMR clean-ups at import (`omr/fixscore.js`, run by `pdf-import.js` before saving; not in the generic parser):** (1) lyric "verses" with < 15% of the main verse's syllables are OCR artifacts — a lyric line read a bit low gets number 2 (folded into the main verse where it has no syllable: "See, | people get mean…"), footnotes/markings under the staff ("See additional lyrics", "gently") are dropped; (2) if the score has no tempo, the `= NNN` from Audiveris's log line `No beat unit in metronome line "… = 133"` (OCR missed the ♩) becomes a quarter-note `<metronome>` + `<sound tempo>` in the first measure. (3) octave clefs: the engine's evidence for the 8 is borderline and pixel-dependent (on the user's iPhone only 8 of 14 Hades clef changes got it, vs nearly all in sandbox Chromium), so in a single-staff part where the octave was found on ≥ 2 systems and on ≥ ⅓ of that clef's systems, the plain ones get the octave and their notes move an octave, up to the next clef (a singer's staff doesn't switch between a clef and its octave variant; the 8 has never been detected on a plain clef in testing). (4) unmarked tuplets: a voice too long by exactly the duration d of a run of k ≥ 3 consecutive equal elements (notes or rests) lasting d → that run is a k:(k−1) tuplet (quadruplets from patch 0007, triplets whose "3" Audiveris missed): durations scaled, `<time-modification>` added, divisions ×k in that measure and restored after. Without this an overfull measure pushes every later measure late. Songbird: 7 measures, song 456 → 450 beats. (5) missed key signatures (`unifyKeySignatures`): on small staves Audiveris often misses a system's key signature and spells that system in C (Wichita Lineman, F major: the voice had no key for 12 measures and the key flipped F/C every system, B♭→B). Its exporter (`PartwiseBuilder`) writes a `<key>` where a staff's key changes (`number="N"` when a part's staves differ), fifths 0 at a system start where the key is missing after one was known, and **nothing** at the top of a page where it's missing (it forgets keys at each page) — so each staff's key is tracked per staff, a page start without a key counting as "none". Readings per *segment* (system starts + measures where a key was written mid-system): a segment where some staves read a key and others none gets the majority non-zero key (ties → the key read most often); a run of all-"none" segments is filled only next to a segment whose staves disagree (all staves changing together = a real key change, kept); a single staff fills only a gap between two segments in the same key; a key written mid-system is trusted (read from accidentals beyond the header — the staves that wrote it decide that segment, and such a boundary is never evidence of misses). Parts at a constant non-zero key offset from the others on every segment are transposing instruments (Audiveris never writes `<transpose>`) and are judged on their own. Re-keyed notes are respelled in time order (voices interleaved via `<backup>`): no printed `<accidental>` → the key's alteration; printed accidentals carry to later notes of that staff/step/octave in the measure, tie continuations keep their start's pitch. Keys are rewritten where they change and at every page start (idempotent). Synthetic cases in tools/keycases.cjs (C song with a real change to D♭, B♭ clarinet + voice, SATB carry, page-start miss, per-staff key, ties…); real scores other than Wichita are untouched. Changes are logged as `[fix] …`. **Download MusicXML** saves this fixed, titled `.musicxml` (not Audiveris's raw `.mxl`). The Sing page runs `fixOmrScore` again whenever it loads or downloads a song whose `<software>` is Audiveris, so songs saved by older versions get newer fixes without re-converting (the clean-ups are idempotent; the tempo one needs the log, so it only runs at import).
- **Boxed inserts (v52, `dropInserts`, first clean-up):** Musicnotes prints piano fills ("Fill 1… Play Fill 1 (2nd time)") as small boxed systems at the foot of a page; Audiveris reads them as measures of the song where they sit, so the melody got silent bars at page breaks (Piano Man: "mak-in' | love" waited a bar). A system is dropped from every part only when the melody's staff isn't in it (its measures have no `width` and no notes), it restates the time signature already in effect, and it's < 75% of the regular systems' width or > 2× their left margin; the `<divisions>` and the last `<key>`/`<clef>` per staff inside move to the next measure's leading attributes where it doesn't set its own (Audiveris fills a part hidden in the box with that part's *next* system's clef and writes none there when it's the same, so the box can hold the only record of a clef change — v53). Piano Man: 5 fills, 12 measures; the intro and interludes (full width, no restated time) stay; no other test score affected. **Stray 8va:** in a single-staff part, treble 8va clefs among plain ones are reverted (notes down an octave) unless they're ≥ ⅔ of its G clefs (a piccolo) — Piano Man's CODA II "𝄌𝄌" above the voice clef was read as the 8 (`G_CLEF_8VA with an 8 above`, grade 0.35), putting "And the piano, it sounds like a…" at G6. This runs before the octave-clef spreading, which for G clefs now only spreads an 8vb (a tenor clef the engine saw on some systems) — two misread coda signs used to move a whole voice up. tools: synthetic cases in the scratchpad (clefbox, vabox, tenor, twocoda).
- **One PDF = one score:** Audiveris starts a new score ("movement") at an indented system; Wichita Lineman's indented Coda system made it export `mvt1` (pages 2–3) and `mvt2` (page 4) and the worker kept whichever path it had 300 ms after the first export (phone: page 4 only; desktop: pages 2–3) — with no failed sheet reported. Now `-constant org.audiveris.omr.sheet.ProcessingSwitches.indentations=false` (the switch only drives movement starts in `SystemManager.allocatePages`), and as a safety net the worker collects every `exported to` path (pending while an `Exporting sheet(s)` line has no export yet; done on `Book stored`/`Closing {Score` or 2 s after the last export) and posts `mxls[]`; `pdf-import.js` joins several with `joinMovements` (fixscore.js: measures appended to the part with the same name, else id/position; a missing part gets whole-measure rests; each joined score's first measure gets `<print new-page="yes">` so key/line logic sees the boundary; logged `[fix] N scores (movements) joined`).
- **Title:** best source first — the PDF's own text layer (`pdfprep.js` `textLines`: each page's 8 largest lines that are words — Musicnotes draws the notation with a font, "{} mf", "Ï Ï"; `omr.js` `pdfTitle`: on the pages up to the first music page, the largest line that isn't a publisher line ("Authorized for use by", ©, "Words and Music by"…) and is ≥ 85% of the largest words on its page, so a rejected title doesn't fall to a credit; ALL CAPS takes the mixed-case spelling from another line, e.g. the title page, else Title Case except short words like "SOS"), then the file name when it's clearly a title (Musicnotes `Wichita_Lineman_-_F_Major_-_MN0305807` → "Wichita Lineman", even "1999"; or anything but a camera/scanner default like "Scanned Document 2", "IMG_0042"), then the largest-font page-1 `<credit-words>` (OCR: no publisher lines, no letters-and-digits run together like "Blzmaj7"), else the file name; `movement-title` is rewritten before saving. Scans have no text layer (Songbird → file name). tools/titlecases.cjs.
- **Tempo from the PDF's text:** `pdfprep.js` `tempoMark` finds "= 104" in a page's text (the number is text; the note is a music-font glyph — read when it's SMuFL U+ECA3/ECA5/ECA7 (+ECB7 dot) or Unicode ♩♪𝅗𝅥, else unknown; a range "= 92-96" takes the first number; "= about 76", "= ca. 66", "≈ 120" read the number; with no note symbol, "in 2" / "in one" on that row or the one above gives `felt` beats per bar — The Longest Time: "Bright rock and roll, in 2 (𝅗𝅥 = about 76)" with the half note drawn as a picture, cut time → ♩=152); `omr.js` returns the first music page's as `res.tempo` ({bpm, unit, dotted}); `restoreTempo` (fixscore) prefers it — added unless the first measure already has a tempo (a later mark the engine read doesn't block it) — over Audiveris's log line (OCR digits, position unknown: only used when the score has no tempo at all; it reads "= about 76" and "in 2" too — v61, before which a missed note symbol plus "about" left the song at the default ♩=90). Music *text* fonts draw notes as letters (Finale Maestro, Sibelius Opus Text: w whole, h half, q quarter, e eighth, x sixteenth, "." the dot), so the text layer reads "h. = 58": a token that is just one of those letters (+ dot) sets the unit (v52; Piano Man's "Fast three, in one 𝅗𝅥. = 58" had come in as ♩=58 instead of ♩=174). tools/tempomark.mjs. Unknown beat unit → the bar divided by `felt` ("in 2" in 4/4 or 2/2 → half; "in one" in 3/4 → dotted half), else the meter's usual one: dotted quarter in 6/8, 9/8, 12/8, half in cut time, else quarter (`<sound tempo>` in quarters: ♩. = 66 → 99). The user's phone conversion of Wichita Lineman missed "♩ = 104" and played at the default 90.
- **Jars:** GUI-only libraries are not shipped (itext, jfreechart, github-api, jackson, jgoodies, commonmark, jna — `SKIP` in build.sh / `JARS` in omr.js): CheerpJ reads each classpath jar's index (~0.4 MB) up front. Verified identical output without them.
- **Rendering:** pages are binarized, counting pixels darker than ~80% white as ink (`< 200000` in `pdfprep.js`). pdf.js anti-aliasing left gray glyph edges that cut lyric recognition from ~44% to ~15%; the dark-leaning cut (slightly bold glyphs) beat a 50% cut on all four test scores (Killing Me Softly 87% → 98% of syllables) with identical notes.
- **CheerpJ 4.2 JIT bug (fixed in the build, v24):** once warm, CheerpJ 4.2/4.3 miscompile code that allocates a 2-D primitive array in one shot (`new double[m][n]`, bytecode `multianewarray`) and fills it element by element — Jama's `Matrix.getArrayCopy` — so every circle fit behind slur/tie detection threw "Matrix is singular" after ~70 calls: page 1 got fewer slurs, pages 2+ got **none** (ties lost → held notes played twice on the Sing page, tie curves misread as fermatas). `StripVolatile.java` now also rewrites every `multianewarray` of a 2-D primitive array (178 sites across the jars) into a call to a generated `cheerpjfix/Arrays2D` helper that allocates row by row; verified natively with `-Xverify:all` (identical output) and in the browser (slurs per page = native, ties in 44 measures = native). Probe tools: `/home/user/cjtest/jama` (`LuProbe`, `JamaProbe`). CheerpJ 5.0 doesn't have the bug.
- **Checking a conversion beyond notes:** `score_omr.py` compares notes one by one and can't see ties; also compare the Sing parser's merged note count with the hand transcription's (250 for the test score) and the measures with `<tie>` against native Audiveris (44). Per-sheet "Slurs: N" log lines vs a native run catch engine regressions.
- **Exit:** `omr.js` reads the `.mxl` as soon as Audiveris logs "exported to …" (CheerpJ threads parked in a queue don't wake on interrupt, so executor shutdown would sit out its grace delay; `graceDelay=1` too).
- **Accuracy on the test score** (vs a 3-way reconciled hand transcription, 311 sung notes): notes 100% found, pitch 99.7%, rhythm 100%, melody notes after merging holds 250 = hand transcription's 250 (v24; 300 before the JIT fix), lyric syllables 95% in the browser (98% native Audiveris; was 37% before patch 0004 + the darker binarization — the rest are one-letter OCR slips like `ly`→`y`). Synthetic scores (Amazing Grace, Oh Susanna, Greensleeves, rendered with Verovio) are 93–100% lyrics, 100% notes. Audiveris also drops "rhythm-slash" multi-bar rests. (The Sing page now unfolds repeats, so a converted song's melody-note count in performance order is larger than the written 250.)
- **First-run download** ≈ 60 MB (CheerpJ runtime ~24 MB from its CDN, jars ~18 MB, OCR ~16 MB); ~11 min for 6 pages in desktop Chromium.
- **One conversion per page load** (Audiveris global state); "Convert another" reloads.
- **One conversion per browser, clean slate each time:** CheerpJ's only writable mount, `/files` (also `java.io.tmpdir`, not overridable), is one IndexedDB database per site (`cjFS_/files/`). Two engines at once (two tabs) corrupt it, and since the worker is killed, Java never deletes its temp files (~2 MB per run). So `omr-worker.js` takes a Web Lock (`resonate-omr-engine`; a second tab gets a clear "already running in another tab" error) and deletes that database before starting.
- **Music font from memory:** `omr-worker.js` fetches `omr/fonts/Bravura.otf` (copied out of the jar by build.sh) into `/str/Bravura.otf` and sets `audiveris.fonts.dir=/str`, instead of `Font.createFont` copying it into IndexedDB.
- **The 0x0 symbol crash (Nov 2026, one user report, not reproduced):** every sheet failed at HEADERS with `Width (0) and height (0) cannot be <= 0` — Bravura was created but FreeType (wasm, in CheerpJ's natives) returned empty glyph outlines, which OpenJDK reports silently. Same PDF works in headless Chromium and WebKitGTK 2.52 here; all 670 symbols in all 6 music fonts render identically to native. Patch 0005 makes it fail loudly with a browser hint; the log now starts with the user agent / threads / RAM, and Details has **Copy log** — ask for that log if it recurs.
- **Failures surface in the UI:** `omr.js` turns `Sheet#N failed…` lines into `failed: [{page, step, reason}]` (result card lists pages left out) and maps "font unusable" / "no page read" to plain-language errors.
- **Speed:** on the user's iPhone ~5 min for the 9-page Songbird scan (~30 s/page); the sandbox's headless Chromium is much slower (~2 min/page) — don't base user-facing estimates on it. ~2 min/page in sandbox Chromium once warm (it was ~1 min/page while slurs were silently broken, see below); phones slower. Step timeout raised to 2 h. CheerpJ 5.0 was tried: correct, but 17½ min for the same 6 pages (its BEAMS step ran ~5× slower).
- **Never commit test scores** (e.g. the user's licensed Musicnotes PDF) — test from outside the repo (`/home/user/sitetest` symlinks `public/` as `/resonate/`).
